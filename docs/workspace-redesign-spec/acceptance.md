# 工作台重设计验收规格

状态：验收口径，所有新增重设计项和三个规划案例默认“待验证”。本文列出可操作检查，不把计划写成结果；仅有代码存在、fixture、静态截图、单次局部观察或文档描述时，不得填写 PASS。

## 验收原则

主代理在浏览器中执行工作台人工验收，检查 1440px 和 1280px 桌面视口，并按需覆盖现有窄屏降级。子代理只能提供文档、代码审查和可重复检查结果，不能替代主代理的目标浏览器证据。

不增加 Playwright E2E 门槛。代码层必要检查使用项目现有 pnpm 命令和案例检查脚本；浏览器交互、真实生成、资源请求、原生下载和 IndexedDB 故障按各自证据类别报告。未执行、环境阻断、用户手动确认和自动检查通过必须分开写。

本轮只验收重设计实际影响的布局、操作映射、状态和关键兼容回归，不要求把旧阶段文档列出的全部历史未验收项重新补齐。旧 A–F 证据继续按原文保留；只有当重设计直接触及某项（例如项目切换、导出对象、旧案例入口或预览工具栏）时，才在本文件中加入对应回归。

## 状态验收细则

### 空白项目

1. 通过工作台入口进入未带案例的空白项目。
2. 左栏消息为空，底部只有一个输入框；顶部显示项目名、无已接受版本和未保存。
3. 右栏可以显示模板加载、Sandpack 启动或空态，但不得出现伪造的 assistant 消息、版本卡片、运行成功或保存成功。
4. 输入需求后才开始请求；示例体验入口打开预置成果时不发送模型请求。

对应 `A-STATE-01`、`A-WR-05`。

### 执行中与耗时

1. 生成、编辑和聊天分别记录可读的运行状态；生成/编辑显示阶段和当前步骤，聊天显示回复状态。
2. 阶段卡可显示已接收步骤、客户端事件间隔和总等待，但文案要说明“含网络”或“用户等待”。`GenerationStatusPanel` 的客户端间隔不是服务端节点耗时，也不能用它推导后端阶段性能。
3. 执行期间项目切换、新建、恢复和删除按保护规则处理；不因点击预览或工具栏而丢失输入。

对应 `A-STATE-02`、`A-STATE-07`。

### 候选与应用

1. 收到 `files + done` 只表示候选已收到，不能直接写入已接受结果。
2. 候选面板显示摘要、基线 hash、文件变更、资源引用和 L0–L5 层；候选预览可以运行，但不得更改 currentFiles、已接受代码/版本或普通导出对象。按既有逻辑，合法的候选相关用户/assistant 消息可以追加到主会话，不要求把消息本身隔离。
3. 校验未通过、基线冲突或候选过期时应用按钮不可用；放弃后候选消失，原工作副本可继续保存/恢复。
4. 应用成功后才创建已接受版本/更新工作副本；仍需用户手动保存到 IndexedDB。

对应 `A-WR-09`、`A-STATE-03`。

### 失败、取消和重试

1. 模型失败、EOF、429/环境阻断、模板失败、构建错误、运行错误和外部超时在 UI 中使用不同原因或类别；已有完整结果/旧画面是否保留要说清楚。
2. 请求重试是重新执行原始模型请求，产生新的模型运行记录；预览刷新/重试只重新运行 Sandpack，不新增模型 run，也不会静默把失败候选应用到项目。
3. 取消后停止接收后续结果并忽略迟到结果；迟到结果不能创建新的候选。取消前已经存在的候选按既有隔离逻辑保留或处理；文案不得声称供应商模型调用已经完全停止。
4. 失败和取消不会改变手动保存状态；用户可在当前内容基础上主动重试或保存。

对应 `A-STATE-04`、`A-STATE-05`。

### 保存失败与切换项目

1. 保存失败时保留编辑器文件、消息、候选隔离和 dirty 状态，显示可理解错误；当前页面不能被清空或悄悄恢复旧快照。
2. 在 loading、生成、assembling 或候选存在时，切换/新建/删除/恢复按代码已有保护阻止或提示；这些状态不能通过直接点击顶部入口绕过。
3. dirty 时给出保存并继续、另存为并继续、放弃当前修改、取消等选择；取消保持原项目和输入，保存失败不得继续切换。
4. 成功切换后只加载目标项目的消息、工作副本、版本和可序列化运行摘要；旧项目不被新项目的输入、候选或保存写入。

对应 `A-STATE-06`、`A-STATE-07`、`A-WR-10`、`A-WR-11`。

## 导出和耗时证据分类

| 项目 | 可以由代码/fixture说明 | 必须由用户或主代理现场确认 |
| --- | --- | --- |
| 生成耗时 | 状态字段存在、计时口径、夹具事件间隔 | 真实模型请求的用户等待时间、失败/取消行为、不同环境差异 |
| 预览等待 | ready 判定由构建成功 + `app-mounted` 组成，重试入口存在 | 目标浏览器中模板加载、构建、挂载、运行错误和超时表现 |
| 代码导出 | 选中的文件 map、manifest 和导出函数调用关系 | 原生下载是否完成、ZIP 解压、依赖安装、导出构建和远程资源请求 |
| IndexedDB | schema、事务、修订冲突和失败保护的 fixture | 浏览器配额、损坏记录、清站点数据、双标签冲突和真实恢复 |
| 案例功能 | 固定源码中的路由、数据和检查脚本 | Sandpack 中的实际搜索/筛选/表单/抽屉/主题交互，尤其是三份新规划案例 |

任何一项没有现场证据时，应写“未验证/手动待确认”，不能写“稳定”“已支持离线”“导出成功”或“真实链路通过”。

## 代码检查口径

改码后至少由主代理在合适工作区执行并记录：

- `pnpm --dir frontend exec tsc --noEmit`；
- `pnpm --dir frontend run lint`；
- `pnpm --dir frontend run build`；
- 相关案例的静态组装/一致性检查（例如已有案例的 `--check` 或 descriptor 检查）；
- `git diff --check` 以及改动范围审查。

这些命令只证明对应代码/文件检查通过，不替代浏览器人工验收。当前仅新增规格文档时，不把上述命令的未来要求写成已经执行的结果。

## 交付前最低记录

交付重设计实现时，验收记录至少要能回答：使用哪个视口、哪个项目/案例、前置保存状态是什么、执行了什么动作、观察到什么结果、是否触发真实模型或静态案例、导出对象是什么、证据存放在哪里。新案例还必须列出拟定 ID 是否已升级为实际 descriptor，以及真实 run、人工修正、资源许可和离线/ZIP 限制。
