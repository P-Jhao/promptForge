# 05 项目与变更契约

本文件定义对象之间的逻辑关系和不可违反的语义，不规定必须使用哪一个 API、数据库表、状态管理库或路由实现。接口可以变化，但下列身份、生命周期和保护关系必须保持可追溯。阶段 F1/F2/F3 已实现主会话、删除和版本体验代码，并由对应 fixture、前端 tsc、lint/build 检查；完整浏览器现场和真实聊天链路仍未验证。

## 对象边界

### Project（项目）

项目是用户可重新打开的长期工作单位，也是唯一的主会话边界，至少有稳定 `projectId`、名称、创建/更新时间、当前工作副本指针、已接受版本指针和 schema 版本。项目名称可以由用户或需求意图更新，但名称变化不能生成新的项目身份。一个项目只对应一个主会话；主会话消息复用现有 `Project.messages`，不新增通用 `Session`/thread 对象或跨项目消息池。

新建项目创建空白消息、文件和版本集合；打开项目恢复该项目已保存的 `Project.messages`、当前文件、已接受版本和必要运行摘要。已有主会话要求另一个项目时，应先确认创建独立项目；用户可选择带入背景消息或需求摘要，但原项目文件、工作副本、候选和版本不改变归属。

### Workspace copy（当前工作副本）

工作副本是当前编辑器实际内容及其资源引用、编辑状态和最近保存信息。它可以与最近一次生成版本不同：用户的手改、格式化或资源替换都属于工作副本。`dirty` 表示内存工作副本相对保存快照有变化，不表示生成失败。

### Accepted version（已接受版本）

版本是不可变的文件快照和元数据，至少关联项目、创建 run、输入需求、父版本（如有）、文件清单/hash、验证摘要和接受时间。版本一旦被接受，不因后续编辑而原地变更；新的修改产生新的候选或版本。

### Candidate（候选）

候选是生成、导入或修复产生的暂存快照，至少关联 `candidateId`、`baseVersionId` 或 `baseWorkspaceHash`、来源 run、文件 map、资源清单和验证状态。候选生命周期为“创建 → 校验中 → 通过/拒绝 → 接受或保留为失败记录”；未验证等同于未接受。

候选不通过校验时可以供用户查看差异和错误，但不能自动替换已接受版本或有未保存改动的工作副本。候选通过约定校验后仍必须由用户明确确认应用，工作副本和版本指针才可以原子地前进；首版不自动接受候选。

### Run（一次运行）

run 表示一次生成、重试、验证、修复或预览尝试。至少记录 run 类型、触发来源、开始/结束状态、输入需求摘要、base 身份、模型/模板版本（不含密钥）、客户端/服务端诊断、取消/超时/失败类别和输出候选。重试是新 run，不能覆盖旧 run 的失败事实。

### Resource（资源）

资源包括图片、字体、依赖包和其他被代码引用的非源码内容。每项至少有逻辑路径或 URL、来源、内容类型、大小、hash、许可/交付限制和当前状态。宿主应用的 URL 可访问，不等于导出项目或 Sandpack 文件 map 已经拥有该资源。

### Frozen case（固化案例）

固化案例是经过真实 run 和验收后变成只读分发资产的一组文件、资源和元数据。案例必须有独立 case ID、入口、manifest、来源 run/模型信息、需求摘要、修改说明和验收记录。固化后打开案例不重新调用模型，但仍需按案例资源和预览状态执行检查。

这里的“必须有真实 run 和验收记录”针对第二阶段新增的任务看板案例。第一阶段小说案例是已披露来源的 legacy 预置成果：它由 `backend/mock` 组装，两个场景共用 48 文件，不能回溯补写成真实生成案例；第二阶段不要求它满足新任务看板的真实来源条件。

## 文件和基线身份

文件 map 的路径必须规范化并限定在项目范围内；路径遍历、隐式绝对路径、重复路径和超限文件应在进入候选前拒绝。每次可继续修改的基线至少包括：

- 规范化后的当前文件 map 或可重建的 patch；
- 文件内容 hash，以及计算方式和 schema 版本；
- 项目 ID、版本/工作副本 ID 和生成上下文；
- 资源清单及资源 hash；
- 用户可见的 prompt、附件引用和相关对话消息 ID。

当前编辑文件优先于最近生成文件；发送时必须冻结编辑器中的完整快照，包括未保存编辑。若只发送文本 history 而没有当前文件或等价 patch/base 身份，就不能声称实现了“基于当前编辑代码继续修改”。完整 `Project.messages` 作为项目主会话持久化，但 edit 默认只使用最近 6 条消息作为上下文；更早消息不被默认为模型已知，界面不能声称拥有完整会话记忆。

## 修改和候选生命周期

一次修改的逻辑过程是：锁定当前 base → 生成新候选 → 校验候选 → 报告差异和保留结果 → 用户明确确认应用 → 写入新的工作副本/版本。首版不自动接受候选；生成期间继续发生的本地编辑不能被结果写回覆盖。解释和讨论走普通 `chat` 时只追加消息，不创建候选或版本；空项目的新需求由内部判定为 `generate`，有代码且明确修改由内部判定为 `edit`，歧义必须先澄清。

当候选只增加功能时，也要验证原有功能保留；“输出包含新文件”不等于“保留了旧行为”。修改请求必须能回答：以哪个文件状态为基线、改变了哪些文件、哪些用户编辑被保留、哪些资源被替换、验证覆盖了什么。

## 并发和 base 冲突

多标签页、恢复期间编辑和后台生成都可能让 base 过期。接受候选前重新比较 base hash/版本指针：

1. 相同：继续进入校验/接受流程；
2. 不同：进入冲突，保留两侧快照和差异；首版不自动合并，也不以“可安全合并”替代用户确认；
3. 用户选择以最新工作副本为基线显式重新请求，或保留/放弃候选后，才产生下一步可追溯记录。

用户选择保留当前编辑、以候选为新基线或重新生成时，都要产生可追溯记录；“以候选为新基线”仍须经过明确的重新请求或应用流程，不能静默写入。冲突处理本身失败时，两个快照都必须可恢复。

## 保存和恢复语义

浏览器本地 IndexedDB 已用于首版 React 项目保存；仓储接口仍可替换，云同步不在本阶段范围。项目包含 `Project.messages`、文件 map、版本、运行记录和资源索引，写入应以项目快照为单位，带 schema 版本和可检测的完整性信息，避免只写入消息而漏掉文件或只写入版本而丢掉 dirty 工作副本。

保存成功表示目标快照已完整写入并可读回。保存失败、序列化失败、配额不足或页面离开时，仍存在的内存工作副本是用户可见真相；界面明确显示未保存，页面关闭后不承诺内存仍保留。恢复先读取并校验快照，再替换内存状态；若当前 dirty 或读到新版本，先进入保护/冲突状态。

“重新打开”至少恢复项目名称/ID、唯一主会话的当前文件、最近已接受版本、版本列表、`Project.messages` 和最近 run 摘要。旧版本不可读时不应让整个项目消失；应保留可读取的工作副本并标记受损版本。如果能从存储层检测到数据被清除，可以说明本地存储已被清除；否则只能说明“未找到本地项目”，并列出清站点数据、首次访问或浏览器变化等可能原因。没有外部副本时引导用户使用此前导出的源码，不能声称存在服务端备份。

用户选择已接受的旧版本恢复时，先检查当前工作副本是否 dirty。若 dirty，必须让用户保存、另存、放弃或取消，不能直接覆盖。用户确认恢复后，直接以被选快照创建新的恢复版本和工作副本，按项目内下一个自动数字序号记录来源版本与恢复时间；不删除该版本之后的任何历史版本，也不把旧版本原地改写。恢复版本沿用被选快照，不继承或伪造新的运行校验通过证据；用户可以继续编辑或再次导出，后续修改仍按候选校验和明确应用流程处理。

## 项目列表、删除和失效写入（阶段 F2 已实现，代码检查已通过；浏览器现场未完整验证）

项目列表提供重命名和删除入口。重命名只更新展示元数据，不改变 `projectId`、主会话消息、文件、工作副本或版本身份。

删除是明确的本地删除操作，必须展示并处理项目记录、文件、`Project.messages`、工作副本、版本、候选、run、验证/恢复记录、资源索引和其他关联记录。删除前检查 dirty 工作副本、进行中的生成/写入/验证/修复、未接受候选和其他标签页占用；任一条件未解决时阻止删除，或要求用户先完成明确的保存、取消、放弃或关闭占用标签页操作。已完成且不再写入的预览不单独阻断删除。

删除使用一个可回滚的本地事务。事务失败时保留项目列表项、内存工作副本和可见错误，不以部分清除结果隐藏项目；当前项目成功删除后清除当前项目指针并进入空白入口。旧标签页的迟到事件或保存必须携带删除前的修订/写入者身份，仓储拒绝已删除身份的写入，不能静默复活项目。首版不要求回收站、云同步或后台恢复服务。

## 存量 IndexedDB 迁移（阶段 F2 已实现，legacy fixture 已检查；真实故障现场未验证）

迁移只补充可选字段和明确默认值。没有主会话标记的既有项目归入该项目的默认主会话；已有消息、文件和历史版本按原记录保留，不凭空补写消息、运行、接受或恢复历史。迁移后的 schema/完整性检查失败或记录损坏时要显式报告并保留可读取部分，不能静默重置数据库或隐藏项目。

## 版本序列、标签和消息卡片（阶段 F3 已实现，代码检查已通过；浏览器现场未完整验证）

顶部项目栏持续显示项目名、当前已接受版本和保存状态；内部 revision 可留在诊断中，普通 UI 不把它当作用户版本号。项目内已接受版本按自动递增的数字序列分配；可选版本名和备注只是元数据，手写 `1.0.0` 不能改变 `versionId`、排序、hash 或快照。

聊天卡片要区分历史版本、当前已接受版本和未接受工作副本。普通 `chat` 只追加 `Project.messages`，不创建版本；手改、格式化或手动保存工作副本也不创建已接受版本。没有已接受版本时显示“尚无已接受版本”，不伪造 v0。

确认恢复 v2 时，直接创建新的恢复版本和工作副本；已有 v4 时新的恢复版本为 v5，并记录 `restoredFrom=v2` 等来源，v3/v4 继续保留。恢复版本只沿用被选快照，不继承或伪造新的运行校验通过证据；恢复后仍需显式手动保存本地项目快照，版本标签修改不改变来源、快照或版本身份。

## 运行数据与源码数据

项目保存默认承诺源码工作副本和项目元数据。生成应用运行时的任务新增、状态切换、筛选选择等属于另一层：

- 固定案例可用固定 seed 保证每次启动有相同初始任务，供功能验收比较；
- 若某一案例要在刷新后保存任务数据，必须在案例元数据中单独声明其存储行为；
- 不因为保存了 Sandpack 文件就承诺任意案例内存状态、第三方 iframe 状态或外部服务数据会恢复；
- 运行数据的保存失败不能覆盖项目源码，也不能把源码恢复误报成应用数据恢复。

## 导出语义

导出默认针对当前工作副本：包含当前文件内容、项目需要的模板/配置、已解析且允许交付的资源和一份 manifest。若用户明确选择已接受版本或固化案例，应把选择的 snapshot ID 显示出来；不能让“导出”在后台悄悄回退到旧生成文件。

导出前核对代码中的资源引用与实际 ZIP 条目。小说案例的固定远程封面 URL 只进入 manifest 的 `externalResources`，不作为 ZIP 本地文件；浏览器 fetch 成功不能单独证明导出项目部署路径正确，联网解压后的项目启动/构建仍需现场验证。资源无法获取时，要么阻止生成不完整包并说明，要么在 manifest 中显式列为缺失，由产品决定是否允许下载。

## 安全和数据保护

项目 ID、文件路径、文件大小、资源 URL、模型输出和诊断消息都要经过输入校验和输出限制。禁止把模型密钥、OSS 密钥或用户凭据写入版本、固定案例或环境示例。外部 URL 要有允许范围、超时和大小边界；错误消息显示必要的定位信息，不把完整敏感请求回显给不应看到的用户。

验证和修复只能读写当前候选及其临时资源，不能用一个未授权的候选覆盖其他项目。清理旧版本、删除资源或清除本地项目属于用户可感知的删除操作，应在执行前指出具体对象，并保证当前工作副本已有可恢复副本或明确提示风险。
