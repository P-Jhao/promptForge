# 05 项目与变更契约

本文件定义对象之间的逻辑关系和不可违反的语义，不规定必须使用哪一个 API、数据库表、状态管理库或路由实现。接口可以变化，但下列身份、生命周期和保护关系必须保持可追溯。

## 对象边界

### Project（项目）

项目是用户可重新打开的长期工作单位，至少有稳定 `projectId`、名称、创建/更新时间、当前工作副本指针、已接受版本指针和 schema 版本。项目名称可以由用户或需求意图更新，但名称变化不能生成新的项目身份。

### Workspace copy（当前工作副本）

工作副本是当前编辑器实际内容及其资源引用、编辑状态和最近保存信息。它可以与最近一次生成版本不同：用户的手改、格式化或资源替换都属于工作副本。`dirty` 表示内存工作副本相对保存快照有变化，不表示生成失败。

### Accepted version（已接受版本）

版本是不可变的文件快照和元数据，至少关联项目、创建 run、输入需求、父版本（如有）、文件清单/hash、验证摘要和接受时间。版本一旦被接受，不因后续编辑而原地变更；新的修改产生新的候选或版本。

### Candidate（候选）

候选是生成、导入或修复产生的暂存快照，至少关联 `candidateId`、`baseVersionId` 或 `baseWorkspaceHash`、来源 run、文件 map、资源清单和验证状态。候选生命周期为“创建 → 校验中 → 通过/拒绝 → 接受或保留为失败记录”；未验证等同于未接受。

候选不通过校验时可以供用户查看差异和错误，但不能自动替换已接受版本或有未保存改动的工作副本。按接受策略明确接受后（建议默认由用户确认），工作副本和版本指针才可以原子地前进。

### Run（一次运行）

run 表示一次生成、重试、验证、修复或预览尝试。至少记录 run 类型、触发来源、开始/结束状态、输入需求摘要、base 身份、模型/模板版本（不含密钥）、客户端/服务端诊断、取消/超时/失败类别和输出候选。重试是新 run，不能覆盖旧 run 的失败事实。

### Resource（资源）

资源包括图片、字体、依赖包和其他被代码引用的非源码内容。每项至少有逻辑路径或 URL、来源、内容类型、大小、hash、许可/交付限制和当前状态。宿主应用的 URL 可访问，不等于导出项目或 Sandpack 文件 map 已经拥有该资源。

### Frozen case（固化案例）

固化案例是经过真实 run 和验收后变成只读分发资产的一组文件、资源和元数据。案例必须有独立 case ID、入口、manifest、来源 run/模型信息、需求摘要、修改说明和验收记录。固化后打开案例不重新调用模型，但仍需按案例资源和预览状态执行检查。

这里的“必须有真实 run 和验收记录”针对第二阶段新增的任务看板案例。第一阶段小说案例是已披露来源的 legacy 预置成果：它由 `backend/mock` 组装，两个场景共用 48 文件，不能回溯补写成真实生成案例；第二阶段不要求它满足新任务看板的真实来源条件。

## 文件和基线身份

文件 map 的路径必须规范化并限定在项目范围内；路径遍历、隐式绝对路径、重复路径和超限文件应在进入候选前拒绝。每次可继续修改的基线至少包括：

- 规范化后的当前文件 map 或可重建的 patch；
- 文件内容 hash，以及计算方式和 schema 版本；
- 项目 ID、版本/工作副本 ID 和生成上下文；
- 资源清单及资源 hash；
- 用户可见的 prompt、附件引用和相关对话消息 ID。

当前编辑文件优先于最近生成文件。若只发送文本 history 而没有当前文件或等价 patch/base 身份，就不能声称实现了“基于当前编辑代码继续修改”。

## 修改和候选生命周期

一次修改的逻辑过程是：锁定当前 base → 生成新候选 → 校验候选 → 报告差异和保留结果 → 按已确定的接受策略接受（建议默认用户明确确认）→ 写入新的工作副本/版本。自动接受是否存在、适用于哪些场景留待决；生成期间继续发生的本地编辑不能被结果写回覆盖。

当候选只增加功能时，也要验证原有功能保留；“输出包含新文件”不等于“保留了旧行为”。修改请求必须能回答：以哪个文件状态为基线、改变了哪些文件、哪些用户编辑被保留、哪些资源被替换、验证覆盖了什么。

## 并发和 base 冲突

多标签页、恢复期间编辑和后台生成都可能让 base 过期。接受候选前重新比较 base hash/版本指针：

1. 相同：继续进入校验/接受流程；
2. 不同且可安全合并：生成合并候选，并把合并结果作为新的候选再次校验；
3. 不同且无法确认：进入冲突，保留两侧快照和差异，等待用户选择。

自动合并不能用“后写覆盖先写”替代。用户选择保留当前编辑、以候选为新基线或重新生成时，都要产生可追溯记录。冲突处理本身失败时，两个快照都必须可恢复。

## 保存和恢复语义

浏览器本地 IndexedDB 是当前建议的存储方向，因为项目包含文件 map、版本、运行记录和资源索引；这一选择仍需在实现前确认。无论存储技术如何，写入应以项目快照为单位，带 schema 版本和可检测的完整性信息，避免只写入消息而漏掉文件或只写入版本而丢掉 dirty 工作副本。

保存成功表示目标快照已完整写入并可读回。保存失败、序列化失败、配额不足或页面离开时，仍存在的内存工作副本是用户可见真相；界面明确显示未保存，页面关闭后不承诺内存仍保留。恢复先读取并校验快照，再替换内存状态；若当前 dirty 或读到新版本，先进入保护/冲突状态。

“重新打开”至少恢复项目名称/ID、当前文件、最近已接受版本、版本列表、必要对话和最近 run 摘要。旧版本不可读时不应让整个项目消失；应保留可读取的工作副本并标记受损版本。如果能从存储层检测到数据被清除，可以说明本地存储已被清除；否则只能说明“未找到本地项目”，并列出清站点数据、首次访问或浏览器变化等可能原因。没有外部副本时引导用户使用此前导出的源码，不能声称存在服务端备份。

用户选择已接受的旧版本恢复时，先检查当前工作副本是否 dirty。若 dirty，必须让用户保存、另存、放弃或取消，不能直接覆盖。确认恢复后，以被选版本创建新的恢复工作副本和恢复记录，记录来源版本与恢复时间；不删除该版本之后的任何历史版本，也不把旧版本原地改写。恢复产生的新状态仍需经过常规校验，用户可以继续编辑或再次导出。

## 运行数据与源码数据

项目保存默认承诺源码工作副本和项目元数据。生成应用运行时的任务新增、状态切换、筛选选择等属于另一层：

- 固定案例可用固定 seed 保证每次启动有相同初始任务，供功能验收比较；
- 若某一案例要在刷新后保存任务数据，必须在案例元数据中单独声明其存储行为；
- 不因为保存了 Sandpack 文件就承诺任意案例内存状态、第三方 iframe 状态或外部服务数据会恢复；
- 运行数据的保存失败不能覆盖项目源码，也不能把源码恢复误报成应用数据恢复。

## 导出语义

导出默认针对当前工作副本：包含当前文件内容、项目需要的模板/配置、已解析且允许交付的资源和一份 manifest。若用户明确选择已接受版本或固化案例，应把选择的 snapshot ID 显示出来；不能让“导出”在后台悄悄回退到旧生成文件。

导出前核对代码中的资源引用与实际 ZIP 条目。根路径 `/book-cover.svg`、相对路径和 Vite `public` 目录的映射要用解压后的项目启动/构建验证；浏览器 fetch 成功不能单独证明导出项目部署路径正确。资源无法获取时，要么阻止生成不完整包并说明，要么在 manifest 中显式列为缺失，由产品决定是否允许下载。

## 安全和数据保护

项目 ID、文件路径、文件大小、资源 URL、模型输出和诊断消息都要经过输入校验和输出限制。禁止把模型密钥、OSS 密钥或用户凭据写入版本、固定案例或环境示例。外部 URL 要有允许范围、超时和大小边界；错误消息显示必要的定位信息，不把完整敏感请求回显给不应看到的用户。

验证和修复只能读写当前候选及其临时资源，不能用一个未授权的候选覆盖其他项目。清理旧版本、删除资源或清除本地项目属于用户可感知的删除操作，应在执行前指出具体对象，并保证当前工作副本已有可恢复副本或明确提示风险。
