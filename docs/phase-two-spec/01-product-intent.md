# 01 产品意图

## 目标

PromptForge 的第二阶段目标，是让用户把一次自然语言生成变成可以继续工作的前端项目。用户应当能看懂结果从哪里来、哪些地方已经被验证，能在代码中做有意义的手改，再让 AI 基于这份当前工作继续修改，并在离开后恢复项目。

当前一期已经能展示和操作一个预置小说阅读管理案例，也能接收真实生成的 SSE 过程。第二阶段要补上演示产品和可交付工作副本之间最关键的连续性：真实结果的可信来源、预览状态的真实性、编辑和版本的保留、失败后的恢复。

## 用户和核心任务

主要用户是需要快速验证前端需求的产品/设计人员，以及需要阅读、修正和导出生成代码的前端开发者。他们的共同任务不是“看一次 AI 输出”，而是：

1. 从一个可操作案例或自己的需求进入工作台；
2. 看到生成过程和当前结果的真实状态；
3. 在预览与代码之间切换，手改一个明确的产品细节；
4. 让 AI 只围绕当前工作继续修改，并检查手改是否保留；
5. 保存、重新打开、恢复、失败重试或导出一份可解释的项目。

## 阶段产品承诺

面向用户的承诺可以概括为：

> 你可以从一个真实来源的案例或自己的 React 需求开始，在当前代码上继续修改；每次结果都能看清状态、验证边界和失败原因，保存后可以回来继续工作。

这项承诺不包括无限制的自动修复、任意沙盒应用数据的通用持久化、多用户协作或 Vue 生成。超出范围的能力不能通过界面文案暗示为已经存在。

## 产品原则

### 结果要可核验

固定案例必须能说明来源、生成方式、固化时的文件清单和验收结果。真实生成案例与 Mock 演示案例必须在身份和文案上分开。预览显示“完成”时，应当有真实的运行就绪证据；客户端收到某个事件或显示了代码，不足以证明应用已经运行。

### 当前编辑优先

用户手改的标题、字段、样式或行为是工作副本的一部分。AI 继续修改时应以当前编辑文件和明确的基线身份为依据。新结果先作为候选，不能因请求完成就覆盖尚未保存或尚未验证的工作。

### 状态要诚实且互相独立

生成流、模板加载、沙盒启动、运行时错误、保存和验证是不同状态。一个状态完成不能替另一个状态背书。例如收到 `done` 只说明生成流结束，不说明 Sandpack 预览 ready；代码编辑器可用也不说明预览已经启动。

### 失败要能恢复

网络失败、上游模型失败、代码校验失败、运行时失败、资源失败和保存失败要能区分。失败后保留最近一次已接受结果及未保存工作副本，给出有边界的重试或修复入口，并说明当前是否有可恢复内容。

### 自动化必须有边界

校验和修复是为了帮助用户判断候选结果，不是把失败隐藏起来。修复必须记录输入基线、每次改动和验证结果；次数、时间、文件大小和资源范围需要有明确上限，具体数值在实现前决定，不能用未批准的数字冒充阶段决策。

## 关键阶段决策

### 预置案例反馈

图片问题和空白/加载问题属于信任问题，应作为第二阶段的首批体验验收点。封面要在案例运行、导出和重新加载语境中都能找到；预览加载提示要由真实模板/沙盒状态驱动，并在超时或失败时提供可行动信息。

### 任务看板案例

阶段新增的任务看板案例必须来自一次真实生成链路。真实生成完成后，经过人工和自动验收，才可以把当前文件、依赖、资源、需求摘要、生成来源和验收结果固化成独立案例。固化后的案例可以像一期小说案例一样无需再次调用模型直接打开，但这只是对已经验收的真实成果做回放，不是通过 Mock 结果伪造一次新的真实生成。

它必须有自己的案例身份、入口和文件清单，不能继续挂在小说案例的 48 文件成果或两个场景路由下。任务数据是否在应用重载后保留，要与源码保存分开说明；如果需要稳定的功能保留测试，可以使用固定 seed，但不因此承诺通用沙盒运行数据持久化。

### React 与 Vue

React/TypeScript 是第二阶段的交付范围，因为现有模板、SSE 生成和 Sandpack 接入都以 React 为基线。Vue 在本阶段只记录评估问题：模板、生成图、预览运行时、校验规则、保存格式和案例验收是否需要独立能力。评估完成前不对 Vue 用户作可用性承诺。

### 保存与恢复

保存的最小产品单位是一个项目工作副本：项目身份、当前文件、已接受版本、对话/运行记录和必要资源引用。浏览器本地 IndexedDB 是建议方向，不是已经拍板的接口；无论采用何种存储，都必须保护未保存编辑，清站点数据、配额不足和多标签页冲突都不能静默丢失用户工作。
