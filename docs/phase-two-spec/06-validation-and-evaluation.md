# 06 验证与评测

验证的目标是回答“这份结果在什么范围内成立”，而不是给生成成功事件换一种说法。每层都记录 `pass`、`fail`、`skipped` 或 `not-verified`，后者不能被汇总为通过。

## 验证层级

### L0：请求和协议完整性

核对请求 schema、项目/base 身份、附件限制、SSE 帧、事件顺序、`files` 结构、`done`、EOF、错误节点和取消行为。`done` 缺失、文件为空、事件格式非法或 base 不明时，候选不能进入接受状态。现有 [`feedbackFixture.ts`](../../backend/test/feedbackFixture.ts) 可覆盖本地 success、fail、EOF、delay、chat 和 429 协议夹具，但夹具通过不表示真实模型通过。

### L1：源码完整性

核对入口文件、依赖、导入路径、资源引用、路径安全、文件数量/大小和类型结构。对 React/TypeScript 结果执行项目约定的类型检查或构建；记录命令、版本、退出码和输出摘要。AST 后处理可以作为生成阶段的一个输入，但不能替代全项目检查。

### L2：沙盒启动与预览

在目标网络和浏览器环境中载入候选，记录模板加载、依赖安装、沙盒启动、真实 ready、运行时错误、资源请求和超时。必须区分：

- 外部 Sandpack/依赖网络失败：运行环境不可用或请求超时，不能直接归因于生成代码；
- 代码/依赖失败：运行环境已启动，但候选编译、导入、资源或运行时报错；
- 产品状态错误：代码可能已经运行，但 UI 仍显示等待，或代码未运行却显示完成。

一期的 Sandpack `TIME_OUT`、本地后端模板 HTTP500 和真实 LLM 未完成链路，都只能作为未验证/失败证据，不能改成 L2 通过。

### L3：固定功能场景

在实际运行的应用中执行固定需求和动作：入口、列表、表单、筛选、状态切换、标题保留、错误恢复、保存/恢复和导出。每个动作记录前置文件 hash、操作、可见结果和截图/日志或自动化断言的来源。应用内任务数据与项目源码保存分别记录。

### L4：保存和恢复

保存后读取同一项目快照，关闭/刷新/重新打开，再核对当前文件、dirty 状态、版本、消息和运行摘要。额外覆盖保存失败、配额不足、schema 不兼容、恢复期间 dirty、多标签页和清除站点数据的说明行为。任何恢复失败都必须保留内存工作副本，直到用户明确放弃。

### L5：有限修复

只对候选运行修复；每一次修复后从 L1 到至少 L2/L3 的相关层重新验证。修复输入、问题、修改文件、尝试序号、消耗的时间/大小/次数和结果都入 run/candidate 记录。修复达到预设边界后停止，展示失败候选和下一步人工操作。

## 有限修复契约

本阶段只接受“有界且可回退”的自动修复。实施前必须确定并记录：

- 单次 run 允许的修复次数；
- 总时间预算和单次校验超时；
- 可修改的文件/资源范围和总大小；
- 哪些错误类别允许自动修复，哪些必须交给用户；
- 失败后是否允许重新生成，如何避免重复同一错误；
- 达到上限、外网不可用或验证不确定时的状态。

阶段 D 的 React 切片采用可读默认值：最多 2 次修复、累计 10 分钟、每轮验证最长 120 秒；这些是实现边界，不是对真实模型耗时或成功率的测量。任何“自动修复成功”都必须指向一个通过相应层级校验的新候选，而不是只报告模型返回了补丁。现场环境若使用不同配置，必须在 run 记录和交接文档中标明。

## 指标定义

指标必须带有 run ID、候选/版本 ID、环境和口径。

### 样本池和分母

真实生成评测和本地协议夹具必须分成两个样本池，不能混合计算成功率：`REAL-EVAL` 只收真实模型/真实服务 run，`PROTOCOL-FIXTURE` 只收 `feedbackFixture.ts` 等可控夹具。每个计划中的尝试都要有样本 ID 和终态分类。

对一个样本池定义 `N_all` 为该指标范围内所有已登记尝试数，包含成功、失败、用户取消/断开、外部环境阻断和未验证样本；`N_cancelled`、`N_env_blocked`、`N_not_verified` 单列报告，不能从分母中删除来美化比例。若一次尝试同时具备多个标记，按约定的主终态计数，并保留附加原因。尚未登记为样本的未来工作不进入结果，但必须在报告中列为未执行计划项，不能写成通过。

建议记录：

| 指标 | 定义 | 注意 |
| --- | --- | --- |
| 请求成功率 | `N_L0_pass / N_real_run_attempts`；分母是 REAL-EVAL 中所有已登记真实生成尝试，取消、环境阻断和未验证均不移除 | 不等于预览成功率；PROTOCOL-FIXTURE 单独报告 |
| 预览 ready 率 | `N_ready / N_preview_attempts`；分母包含尝试启动预览的全部候选，环境阻断、取消和未验证单列且不从分母剔除 | 不能由 `initial/running` 或代码可见推断 |
| 固定场景通过率 | `N_all_requirements_pass / N_scenario_attempts`；每次场景尝试即进入分母，任何未验证条目都不能贡献通过 | 条目缺证据或未验证不算通过 |
| 保留率 | `N_preservation_assertions_pass / N_preservation_assertions_total`；分母是所有登记的具体保留断言，失败、取消或未验证断言都保留 | 需要具体断言，不能只比较文件数量 |
| 保存恢复成功率 | `N_restore_pass / N_restore_attempts`；分母包含全部登记的保存/恢复尝试，写入失败、配额、冲突和未验证单列 | 与运行时任务数据分开 |
| 有限修复收益 | `N_failed_candidates_fixed_and_passed / N_repair_attempts`；分母是所有进入修复的候选，达到上限、取消、环境阻断和未验证都列出 | 必须显示失败和达到上限的样本 |
| 用户总等待时间 | 从提交到用户可看到可操作结果的墙钟时间 | 与客户端事件间隔分开 |
| 阶段接收间隔 | 浏览器收到相邻 SSE 事件的时间差 | 当前实现含网络，不是服务端节点耗时 |
| 服务端节点耗时 | 服务端实际节点开始/结束时间差（若未来提供） | 没有服务端时间时标为未提供 |

不把客户端 `stageTimings` 当作 server node time；也不把客户端取消当作上游模型已经取消。外网不可用要在指标中单独分类，避免把环境失败混入代码质量。

## 三个固定评测场景（拟议）

以下是需求固定场景的候选定义，目的是让后续运行可重复；本轮只写场景和断言，不生成任务数据、不调用模型，也不宣称已有结果。

### EVAL-01：任务看板基础交付

拟议固定原始需求文本：

> 做一个 React/TypeScript 任务看板，展示任务标题、描述、负责人、截止日期和优先级字段；按待办、进行中、已完成三列展示任务；用户可以新增任务、编辑任务、切换任务状态，并用关键词筛选任务。请保留清晰的看板标题、空状态和表单校验。初始版本只需要展示优先级字段，不要求提供按优先级筛选。

验收关注入口可达、任务列表/列可渲染、新增任务、编辑任务、状态切换和关键词筛选可用、代码和资源完整、运行时获得 ready。建议固定一个评测 seed（例如 `task-board-eval-v1`）和任务条目，但 seed 与数据仅是评测配置候选，本轮不生成任务数据；一旦确定，所有 EVAL-01 样本使用同一配置并记录。

### EVAL-02：当前编辑保留与继续修改

从 EVAL-01 的已接受版本开始，用户手改任务看板标题并保存、重新打开。拟议固定增量 prompt 文本：

> 在当前任务看板上增加按优先级筛选。请以当前编辑文件为基线，保留看板标题、已有任务新增、编辑任务、状态切换、关键词筛选、源码中的固定初始任务数据（不要求通用沙盒内存恢复）和优先级字段；不要删除或重建已有入口和功能。

验收要求：标题、已有新增/编辑任务、状态切换、关键词筛选和原有入口保留；优先级筛选可操作；base、候选、接受版本和保存恢复记录可追溯。EVAL-01 初始需求不含优先级筛选，新增筛选的保留性可以归因于 EVAL-02 的增量修改。

### EVAL-03：失败恢复与候选隔离

使用本地可控夹具让生成、预览或验证中的一个环节失败，再执行重试或有限修复。验收要求：错误分类准确；上一份已接受结果和未保存编辑仍可见；失败候选不覆盖当前结果；取消说明只代表停止接收；恢复后能继续验证或导出当前工作副本。

## 评测报告最低内容

每次报告至少列出需求 ID/场景 ID、样本池、`N_all`、取消数、环境阻断数、未验证数、输入 prompt 摘要、项目和 base、run/candidate/version、模型/模板版本、环境、每层状态、总耗时口径、修复次数、保留断言、资源检查、失败分类和未验证项。报告不得把“没有运行环境”“没有真实模型”“没有资源复现”写成通过。
